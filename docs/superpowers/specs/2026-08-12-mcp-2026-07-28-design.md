# MCP 2026-07-28 Strict-Version Migration Design

## Context

Sandrone currently uses `github.com/modelcontextprotocol/go-sdk` v1.6.1 and
exposes one Streamable HTTP MCP endpoint. That SDK predates full support for
the MCP `2026-07-28` revision. The current handler is not stateless, its tests
still describe the legacy initialize lifecycle, and one error test explicitly
exercises an SDK compatibility switch.

MCP `2026-07-28` replaces the initialize/initialized session lifecycle with
self-describing requests and optional `server/discover`, standardizes routing
headers, adds cache metadata to discovery/list/resource results, and removes
transport-level sessions from the new Streamable HTTP model. The official Go
SDK implements this revision in v1.7.0, but intentionally continues to
negotiate older revisions unless an application imposes a stricter policy.

Sandrone will adopt `2026-07-28` as its only MCP protocol revision. Existing
Sandrone tools, resources, prompts, schemas, service calls, and authorization
remain the application contract; only the MCP lifecycle, transport, metadata,
and SDK-facing implementation change.

## Goals

- Upgrade the official Go MCP SDK to v1.7.0.
- Accept and advertise only MCP protocol revision `2026-07-28`.
- Use the new stateless, sessionless Streamable HTTP lifecycle.
- Use the current SDK request, result, capability, cache, and JSON-RPC error
  interfaces directly, without Sandrone compatibility paths for older MCP
  revisions or older SDK behavior.
- Preserve the current Sandrone tool, resource, prompt, schema, output-limit,
  service-layer, and bearer-authentication contracts.
- Prove the new wire behavior with protocol-level HTTP tests in addition to the
  existing semantic MCP test suite.

## Non-goals

- Continue accepting `initialize`, `notifications/initialized`, or any MCP
  protocol revision older than `2026-07-28`.
- Add Tasks or another MCP extension.
- Add application flows that require Multi Round-Trip Requests.
- Adopt deprecated Roots, Sampling, or Logging features.
- Add mutable list notifications or resource subscriptions; Sandrone's MCP
  catalog is fixed when a server is constructed.
- Rename Sandrone tools, resource URIs, prompts, or their business fields.
- Change the HTTP API, CLI service orchestration, storage model, or Agent Skill
  execution priority.
- Fork or copy the official Streamable HTTP transport.

## Chosen Architecture

### Official SDK and one canonical protocol revision

`go.mod` will require `github.com/modelcontextprotocol/go-sdk v1.7.0`.
`internal/entry/mcpapi` will define one canonical protocol revision constant:

```text
2026-07-28
```

The constant owns Sandrone's accepted MCP revision and is used by protocol
policy, tests, and documentation assertions. No list of historical revisions
will be maintained in Sandrone.

The SDK itself supports older peers, so merely enabling stateless transport is
not enough. Sandrone will install a receiving middleware on every constructed
`mcp.Server`. The middleware will:

1. read the version from the current `mcp.ServerRequest` through
   `ProtocolVersion()`;
2. reject the legacy `initialize` method, using the version in
   `mcp.InitializeParams` only to populate error context;
3. reject every request whose version is not exactly `2026-07-28`;
4. return the SDK's public `jsonrpc.Error` with
   `mcp.CodeUnsupportedProtocolVersion` (`-32022`) and
   `mcp.UnsupportedProtocolVersionData`;
5. narrow a successful `mcp.DiscoverResult.SupportedVersions` value to the
   single Sandrone revision.

The structured error data will contain only:

```json
{
  "supported": ["2026-07-28"],
  "requested": "<request version>"
}
```

This middleware applies to both the production HTTP handler and in-memory SDK
servers used by tests. It avoids a transport fork while making Sandrone's
single-version policy explicit at the closest public SDK boundary.

### Stateless Streamable HTTP

The MCP HTTP handler will use these v1.7.0 options:

- `Stateless: true`, required for the `2026-07-28` protocol;
- `JSONResponse: true`, preserving Sandrone's current response mode;
- `PropagateRequestCancellation: true`, so cancelled HTTP requests stop
  conversion, probing, rendering, and other handler work;
- `MaxRequestBodyBytes: mcp.DefaultMaxRequestBodyBytes`, making the SDK's
  4 MiB safety limit an explicit Sandrone transport contract;
- the existing Sandrone logger.

The resulting endpoint does not issue or consume `Mcp-Session-Id`. Standalone
GET and DELETE requests return `405 Method Not Allowed`; the old resumability
and session-deletion paths are not supported. POST requests use per-request
`_meta` and the SDK validates the standardized `Mcp-Protocol-Version`,
`Mcp-Method`, and `Mcp-Name` header mirrors. Header/body disagreement remains
the SDK-defined `HeaderMismatch` (`-32020`) protocol error.

No Sandrone-specific `Mcp-Param-*` annotations are added. They are optional
routing hints and none of the current tool arguments needs to be promoted into
an HTTP header.

### Capabilities and extensions

The server will configure explicit `mcp.ServerCapabilities` for tools,
resources, and prompts with list-change and resource-subscription flags left
false. This prevents the SDK's historical default Logging capability and does
not advertise a change stream for a catalog that is immutable after server
construction.

Sandrone will advertise no extensions. Existing tools, fixed resources,
resource templates, and prompts are registered exactly as today. Management
tool availability remains determined once, from
`MCP.AllowManagementTools`, while constructing the server.

### Cache metadata

The protocol middleware will apply explicit cache metadata after the SDK has
produced a response:

| Result | `ttlMs` | `cacheScope` | Reason |
| --- | ---: | --- | --- |
| `server/discover` | `300000` | `private` | Identity, capabilities, and revision are fixed for the server process. |
| `tools/list` | `300000` | `private` | Tool registration is fixed and may reveal management mode. |
| `prompts/list` | `300000` | `private` | Prompt registration is fixed. |
| `resources/list` | `300000` | `private` | Fixed resource registration is cacheable. |
| `resources/templates/list` | `300000` | `private` | Fixed template registration is cacheable. |
| `resources/read` | `0` | `private` | Definitions may contain credentials and may change through managed storage. |

`private` prevents shared MCP caches from serving authenticated Sandrone
metadata or resource definitions across clients. A zero resource-read TTL
keeps mutable subscription and FileSpec definitions immediately stale.

### Tools and structured errors

Sandrone's tool wrapper will continue using the official low-level
`mcp.Server.AddTool` API because Sandrone validates a success-or-structured-
error output schema and returns field-aware validation errors. The current
generic `mcp.AddTool` helper cannot emit Sandrone's structured error envelope
when input validation fails before the typed handler runs.

The wrapper remains responsible for strict input decoding, defaults, output
validation, and the union output schema. Application failures remain tool
results rather than JSON-RPC protocol failures:

```json
{
  "isError": true,
  "structuredContent": {
    "error": {
      "code": "invalid_argument",
      "message": "..."
    }
  }
}
```

The result will be built directly with current `mcp.CallToolResult` fields:
`IsError`, `Content`, and `StructuredContent`. It will not call `SetError` and
then compensate for historical overwrite behavior. The dedicated
`MCPGODEBUG=seterroroverwrite=1` compatibility subprocess tests will be
deleted. The unrelated sanitization tests currently sharing that file will
move to the main error test file; existing redaction and structured error
tests remain authoritative.

For successful `2026-07-28` calls, the SDK adds `resultType: "complete"` and
per-response server identity metadata. Sandrone does not construct those wire
fields manually.

## Request and Response Flow

1. The existing HTTP bearer middleware authenticates the MCP path.
2. The v1.7.0 Streamable HTTP handler accepts a stateless POST and validates
   standardized MCP headers against the JSON-RPC body.
3. The SDK parses required per-request protocol, client identity, and client
   capability metadata.
4. Sandrone's protocol middleware rejects anything other than
   `2026-07-28`.
5. `server/discover` or the existing tool/resource/prompt handler runs.
6. The protocol middleware narrows discovery and applies cache policy to
   cacheable results.
7. The SDK adds the complete result type and Sandrone server identity.
8. The HTTP handler returns one JSON response. No transport session survives
   the request.

## Failure Handling

- Old or missing lifecycle metadata never falls back to initialize.
- An old `initialize` call returns structured `-32022`, not a negotiated
  legacy result.
- A version mismatch reports only `2026-07-28` as supported.
- Missing required new-protocol metadata remains an SDK protocol error.
- MCP header/body mismatch remains SDK error `-32020`.
- Request bodies larger than 4 MiB use the SDK's
  `413 Request Entity Too Large` behavior.
- A cancelled stateless POST cancels the handler context.
- Sandrone domain and validation failures remain sanitized, structured tool
  errors with `isError: true`.
- Resource lookup failures use the v1.7.0 SDK error behavior; Sandrone will not
  enable the old custom resource-not-found code compatibility flag.

## Files and Ownership

- `go.mod`, `go.sum`: official MCP SDK v1.7.0 dependency graph.
- `internal/entry/mcpapi/server.go`: explicit latest capabilities and
  stateless HTTP options.
- `internal/entry/mcpapi/protocol.go`: canonical revision, strict protocol
  middleware, version errors, discovery narrowing, and cache policy.
- `internal/entry/mcpapi/tool_handler.go`, `errors.go`: current result-field
  construction while preserving Sandrone schema and redaction behavior.
- `internal/entry/mcpapi/protocol_test.go`, `transport_test.go`, and focused
  existing tests: protocol, HTTP, metadata, and regression proof.
- `internal/entry/mcpapi/errors_compat_test.go`: remove the legacy SDK
  compatibility subprocess coverage, move its two current sanitization tests
  into `errors_test.go`, then delete the otherwise-empty compatibility file.
- `docs/reference/mcp.md`: canonical public lifecycle, headers, capabilities,
  cache, body-limit, error, and client-compatibility contract.

No service, domain, adapter, store, Web, or HTTP API ownership moves into the
MCP entrypoint.

## Verification

Focused tests will prove:

- `server/discover` succeeds through raw Streamable HTTP and advertises only
  `2026-07-28`;
- discovery and ordinary responses contain `resultType: "complete"` and
  `io.modelcontextprotocol/serverInfo`;
- the endpoint emits no `Mcp-Session-Id`;
- legacy initialize requests receive `-32022` with only the canonical version
  in `supported`;
- stateless GET and DELETE receive 405;
- required standardized headers work and a header/body mismatch receives
  `-32020`;
- request bodies larger than 4 MiB receive 413;
- discovery/list results carry the five-minute private cache policy;
- resource reads carry zero-TTL private cache policy;
- deprecated Logging and change/subscription capabilities are absent;
- current tools, resources, prompts, schemas, structured errors, body output
  limits, and management-mode behavior remain unchanged.

Verification order:

1. run the new protocol and transport tests;
2. run all `internal/entry/mcpapi` tests;
3. run `git diff --check`;
4. run the repository gate, `make check`;
5. inspect `rg` results for the old SDK version, old protocol revisions,
   initialize-lifecycle wording, `Mcp-Session-Id`, and MCP compatibility flags,
   allowing occurrences only where the canonical reference explicitly states
   that those paths are rejected.
